# План: приблизить @local/dsh-ide к работе внешнего редактора-образца

**Начать с P0 → P1 → P2.** Первый законченный результат: пользователь выделяет функцию, просит изменить её, видит diff прямо у кода, отменяет без следов или подтверждает одним Undo-шагом. Для этого не нужны ни индекс всего проекта, ни отдельный агент, ни новая модель. [Разбор образца и первичные источники](reference-editor-mechanics.md) · [Инвентарь установленной сборки](reference-editor-extension-inventory.json).

## Рабочая база и ограничения

- Цель — **корневой** пакет `@local/dsh-ide` 0.3.0, HEAD `2ce1e0c`. `editor/` — отдельный компактный `@local/dsh-code-editor`, не место для новой IDE. `client.js` уже изменён пользователем (SHA-256 на дату анализа `b18db8db6b35118614d4f2dbad6d07920b70042d3fb2ee3630305a7d8caf5741`). Перед работой посмотреть `git status --short` и `git diff -- client.js`; **не** делать checkout/reset и не подменять файл версией из HEAD. Ищите функции по имени, номера строк могут сдвинуться.
- Не писать заново: в [Host](../index.js) есть `handlers` для `open/save/complete/tree/files/create/mkdir/rename/remove`, настройки и каталог; [Tab](../tab.js) уже вычисляет диапазон и фильтрует результат; [edits](../edits.js) разбирает структурированный ответ и отбрасывает неоднозначные замены. В [Client](../client.js) `acceptGhost` проверяет версию и принимает продолжение с правками одной транзакцией. В рабочей копии уже есть `chatToken`, `insertChatReference`, `quoteFile` и drag-and-drop. Вкладка «Чат» панели диагностики — не основной разговор с агентом.
- Все будущие маршруты и структуры ниже — **предложения**, не существующий контракт Harness. Проверять реальные имена через Cordis Inspect. В этой сессии для `@local/dsh-ide` найден `include:dsh-ide`; отсутствие Config-схемы — не доказательство отсутствия плагина. Не регистрировать выдуманный глобальный слот `sidebar-right`. Сначала использовать уже смонтированный `IdeBody`. Новые Host-модули включать в `files` корневого [манифеста](../package.json); динамический Client не считать обычным ESM-приложением. Не редактировать `vendor/vs`.
- Один пункт — одно обратимое изменение. До и после: `npm run check`, `npm run test:all` из корня. Новые тестовые файлы перечислять в `scripts.test`: список сейчас явный. Если изменены `catalog.js`, `completion.js`, `prefs.js` или `tree.js`, обновить одноимённые копии в `editor/` и проверить [sync.test](../editor/tests/sync.test.mjs). Новые IDE-модули туда не дублировать. При исходном падении записать команду, тест и ошибку; не ослаблять проверку. Для тестов — фиктивный провайдер, без ключей и платных запросов.

## P0. Зафиксировать поведение до изменений

1. В `tests/client.test.mjs` и `tests/edits.test.mjs` найти текущие проверки ghost/phantom. Создать fixture: два небольших файла `main.ts` и `format.ts`, строка вызова и определение, одно совпадение и два одинаковых совпадения, CRLF и кириллица. Поддельный ответ модели должен быть воспроизводимым.
2. Зафиксировать: принятие слова, Esc, переключение вкладок во время ответа, Ctrl+S при открытом многострочном preview, выделение грязного буфера → черновик чата. Отдельно проверить `Save All` и переключение сессии. Записать, какой текст получили `save` и composer, а не только наличие кнопки.
3. Сохранить известные результаты. Если JS-тест проверяет только текст регистрации, добавить тест с моделью и вызовом обработчика либо ручную проверку в настоящем Monaco; не называть заглушку проверкой реального UI. Признак готовности: для каждого сценария известно ожидаемое и фактическое состояние файла, буфера и фокуса.

## P1. Один безопасный предпросмотр, независимый от диска

**Зачем:** сейчас многострочный phantom временно меняет буфер; `acceptGhost` учитывает `phantom.version` и сдвиг координат. Для одной подсказки это реализовано. Переиспользовать эту схему для долгоживущего review опасно: другие команды читают ту же модель. Это риск дизайна, не утверждение, что обнаружена потеря данных.

1. Добавить чистый Host-модуль `proposal.js` и тесты. Предлагаемая запись: `{id, documentId, modelVersion, changes:[{start,end,oldText,newText}]}`. Смещения в UTF-16, `end` исключающий; зафиксировать EOL. При создании отвергнуть выход из буфера, пересечения, дубли и несовпадение `oldText`. Для find/replace вызывать `locateEdits`, не искать «самое похожее» вхождение. Для вставки разрешён пустой исходный диапазон.
2. В `client.js` начать с отдельного режима review: исходник — неизменённая модель, результат — временная модель diff или view zones/декорации. Обе модели не записываются в список вкладок. Dispose preview при закрытии, смене сессии, новом запросе. Сначала сохранить старую отрисовку быстрого Tab; переводить phantom только после сравнения UX.
3. Состояния: `pending → preview → accepted | dismissed | stale | failed`. Перед Apply проверить текущие URI, версию **и** текст диапазонов. `accepted` меняет только буфер через `executeEdits`, с границами Undo; запись на диск остаётся прежней явной командой `save`. Несовпадение → «Файл изменился, запросите новую правку», без записи. Esc закрывает только верхнее окно и возвращает фокус.
4. Готово, когда Ctrl+S до принятия сохраняет пользовательский текст без предложений, Esc сохраняет исходные dirty/undo, повторный Apply не действует, Undo после Apply восстанавливает исходник. Проверить LF/CRLF, emoji перед диапазоном, последний файл без завершающего LF, две вкладки с одинаковым basename. Откат: отключить новую точку входа; формат файлов не меняется.

## P2. Inline Edit для выделения (после P1)

1. В `IdeBody` добавить команду меню «Изменить выделение…» и сочетание `Ctrl+K` только при фокусе Monaco. Если клавиши заняты хостом или пользовательским chord, не перехватывать их глобально: меню всегда доступно. Пустое выделение в первой версии → подсказка «Выделите код»; генерация с нуля — отдельный режим позже.
2. Зафиксировать `documentId`, версию, границы, актуальный текст и инструкцию. Новый `handlers.inlineEdit` в `index.js`: через `sessionOf` проверить сессию, принадлежность документа и доступный workspace, запреты на передачу файла и согласие. В запрос уходит только выделение и ограниченный соседний контекст с понятной надписью, какая модель получит текст. Не выдавать новое разрешение из-за старого opt-in на Tab без проверки его области.
3. Использовать существующий путь выбора провайдера, секретов, отмены и таймаута. Для первой версии достаточно одного ответа `{replacement:string}`; пустая строка означает удаление **только если** это корректный структурированный ответ. Пустой поток, невалидный JSON и обрыв — ошибка, не удаление. Host формирует proposal для исходного диапазона, а не правит файл. Не направлять инструкцию в `sanitizeCompletion`, который оптимизирован под продолжение строки.
4. Показать «Принять / Отмена / Уточнить». Уточнение меняет запрос относительно исходного snapshot, а не уже нарисованного diff. При вводе в обычный буфер или смене файла — отмена + игнор позднего результата по ID. Готово: отказ провайдера не теряет выделение; запрос без согласия не вызывает модель; два поздних ответа не меняют новое окно; принятая правка отменяется одним Undo.

## P3. Tab: очередь следующих мест вместо обязательной пачки (после P1)

1. Не менять фильтры `tab.js`. Ввести настройку «Последовательные правки», изначально выключена. Из **уже проверенных** `locateEdits` строить очередь сначала по текущему файлу, от курсора по расстоянию, при равенстве по смещению. Это наша детерминированная замена предиктора образца; новую модель на каждый Tab не вызывать.
2. Развести действия: видна вставка → Tab принимает вставку; есть следующая цель → показать «Tab: перейти к …»; следующий Tab только перемещает курсор; ещё один принимает показанный фрагмент. Esc очищает цепочку. Когда целей нет, Tab остаётся штатной клавишей Monaco. `Ctrl+→` не подтверждает остальные правки. Непредвиденный ввод инвалидирует очередь; после собственной принятой правки пересчитать координаты оставшихся по дельте и заново сверить `oldText`.
3. Межфайловый переход — вторым изменением: только по явным целям среди открытых разрешённых документов. Показать путь и строку внизу редактора; по подтверждению открыть вкладку, но ничего там не применять. Не угадывать файл по basename. Если версия устарела — снять цель. Тесты: две последовательные правки выше/ниже курсора, переход A→B, закрытие B, отсутствие цели и задержанный ответ. Метрики локально: время от ввода до preview и число запросов на десять принятий; сравнивать с baseline на той же модели, не с рекламной задержкой образца.

## P4. Контекст проекта и поиск по содержимому (можно после P0)

1. Оставить `Ctrl+P` поиском путей. В activity bar добавить «Поиск в файлах» (`Ctrl+Shift+F` внутри IDE). Новый Host-маршрут `searchText` получает `{sessionId,query,limit}` и `request.signal`; отвечает `{matches:[{path,line,column,preview}],truncated}`. Для MVP — литеральное совпадение, без пользовательских regex и без внешних процессов. Строки/колонки в ответе однобазовые.
2. Переиспользовать ограничения `tree.js` и безопасный путь чтения `open`. Проверять разрешённый корень после разрешения ссылок, не читать бинарники, большие и исключённые файлы; отдельная политика AI-исключений перед отправкой. Задать бюджеты, например 50 результатов и 8 МиБ прочитанного **на запрос**, возвращать `truncated`, не «не найдено», если остановились по бюджету. Отмена старого поиска при новом вводе. Поиск локален даже без AI opt-in.
3. Клик открывает файл на строке. «Добавить в чат» переиспользует `insertChatReference`. Для несохранённых правок отличать ссылку на файл от снимка выделенного текста. Показать источник, строки и объём; при недоступном `inputActions` сообщить об этом, не подменять прямой отправкой. Позднее — свежие открытые фрагменты + диагностики Monaco в контекст Tab, только с явным разрешением на **другие файлы**, дедупликацией и общим лимитом.
4. Проверки: запрос не уходит модели; пустой запрос не обходит дерево; игнорируемая директория и ссылка наружу не читаются; одинаковые имена из разных папок различимы; отмена возвращает управление; добавление ссылки не стирает существующий черновик. Индекс вводить только если замер большого тестового дерева показывает проблему: ключ кэша `(workspace, path, version, ignorePolicyVersion)`, при изменении правил инвалидировать до выдачи результатов.

## P5. Изменения агента, диагностика и возврат (после P1; связь с DSH проверять отдельно)

1. Создать панель «Изменения» отдельно от «Траектории» запросов. Сначала источник только собственные proposal: имя файла, число добавлений/удалений, состояния «предложено / принято в буфер / сохранено / конфликт». Поддержать просмотр и отказ по файлу и блоку. До сохранения показать число несохранённых вкладок. Частичный успех нескольких сохранений **не** показывать как атомарную операцию.
2. Хранить ограниченную историю в памяти сессии: до/после принятой правки, версия и ID. Восстановление — отдельное обратное предложение только при совпадении текущего текста с `after`; иначе открыть сравнение и оставить файл как есть. Не восстанавливать Git-ветку, чужие dirty-изменения и не удалять переписку. Перезапуск честно очищает временную историю. Персистентные checkpoints требуют отдельного решения о сроке хранения и секретах.
3. Для правок **внешнего агента DSH** сначала получить объявленный Service/Event через `cordis_inspect_list` и точечный `cordis_inspect_query`. Нужны session ID, рабочий корень, файл, статус и версия; иначе дать «Сравнить с диском» по запросу пользователя. Если исходного снимка нет, пометить «нет исходной версии», а не обещать Undo. Не перехватывать shell/инструменты и не читать приватную БД чата. Review уже сохранённой работы — отдельная команда, подготавливающая запрос в основной чат, а не новая авторизация запуска.
4. Контрольные случаи: агент и пользователь одновременно изменили строку; первый файл сохранён, второй stale; read-only сессия; переоткрытие вкладки; diff соседней сессии не виден. Полезность: пользователь может объяснить, **что предложено, что уже на диске и что можно вернуть**.

## P6. Оболочка IDE и более дорогие функции

| Очередь | Минимальный полезный срез | Когда развивать дальше |
|---|---|---|
| Палитра и фокус | В `client.js` собрать существующие команды меню в каталог `{id,label,enabled,run}`. Из `Ctrl+Shift+P` вызывать тот же обработчик. Развести `Ctrl+K` в редакторе и поиск в основном чате. Добавить статусы Tab/паузы, видимый dirty и возврат фокуса после Esc. | После теста с клавиатурой, светлой/тёмной темой и узкой правой панелью. Не перехватывать сочетания в чужих полях. |
| Диагностики и навигация | В существующей нижней панели добавить «Проблемы»: доступные markers текущей Monaco-модели, переход по URI и позиции. Для языков без источника показывать «диагностика недоступна», а не «ошибок нет». | LSP — только после пилота одного языка: отмена запросов, версия документа, завершение сервера и стоимость памяти проверены. |
| Ask / Plan / Agent | В меню файла предложить «Объяснить» и «Подготовить план»: подготовить черновик в штатном composer с диапазоном и вопросом. Не отправлять автоматически. | Реальный переключатель режима, прогресс инструментов и approvals — только при подтверждённом контракте DSH; надпись в prompt сама по себе не ограничивает права. |
| Rules / MCP / терминал | Показывать уже доступные возможности DSH со ссылкой в их штатный интерфейс; терминальный вывод не путать с диагностической панелью Tab. | Не создавать новый MCP-клиент, скрытый терминал или исполнение workspace-скриптов в IDE. |
| Git / worktrees / несколько агентов | Пометить каждый результат корнем и сессией. Сначала read-only сравнение: выбрать результат, посмотреть diff. | Создание checkout, перенос файлов, commit/push и публикация — отдельные действия с разрешением; никаких автоматических операций. Cloud, аккаунты, синхронизация настроек и биллинг вне плана. |

## Приёмка и передача следующей модели

После каждой карточки проверить Host-тесты, Client-тесты и рабочий UI именно в DSH; отсутствие доступа к живому UI записать как непроверенное. Для ручной приёмки открыть тестовую папку, изменить первый файл без сохранения, запросить замену, перейти во второй и вернуться, отменить, повторить и принять. Проверить содержимое **буфера**, **диска**, **черновика чата** и состояние **Undo** отдельно. Повторить без AI-разрешения и в read-only сессии. Внешний запрос в ручном прогоне — только с согласия пользователя на тестовые данные.

Рекомендуемое первое задание исполнителю: «Прочти P0 и P1. Сегодня выполни только P0. Не меняй поведение и не устанавливай бандл. Верни список проверенных сценариев, исходные падения и недостающие тесты. Следующее изменение — отдельный reviewable diff». Переходить дальше только когда понятен результат текущего шага; при несовпадении имён функций с рабочей копией найти фактический обработчик, а не создавать второй параллельный путь.
